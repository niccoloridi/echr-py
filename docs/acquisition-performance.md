# Acquisition performance and tuning

`echr-py` separates three controls that are easy to conflate:

| Work | Control | Default | Meaning |
|---|---|---:|---|
| HUDOC metadata search | `search --page-size` | 100 | Rows requested per HTTP page; HUDOC permits up to 500 |
| Bounded result selection | `--limit`, `smart-fetch --top` | command-specific | Maximum records retained by the operation |
| Full-text hydration | `smart-fetch --concurrency` | 20 | Maximum simultaneous case-text downloads |
| Language-version acquisition | `versions download --concurrency` | 10 | Maximum simultaneous version downloads |

Individual HTML responses are capped at 32 MiB and binary DOCX/PDF responses
at 256 MiB before they are accepted. Readers stream into bounded buffers, so a
malformed or unexpectedly large response cannot consume unbounded memory.

For a bounded research sample, a representative command is:

```bash
echr-py smart-fetch --article 3 --respondent ITA \
  --top 100 --page-size 100 --concurrency 20 \
  --rich-sections --out cases.jsonl
```

Metadata-only searches are usually substantially faster than full-text
hydration. Increasing `--page-size` reduces metadata round trips. Increasing
`--concurrency` can improve text acquisition until network latency, local
parsing, HUDOC responsiveness or server throttling becomes the limiting
factor. These settings are independent: a page size is not a download worker
count, and a large result limit does not itself create more concurrency.

The Python APIs expose the same controls:

```python
from hudoc_py import search, smart_fetch

metadata = search(article="3", page_size=500, limit=1_000)
cases = smart_fetch(
    article="3",
    top=100,
    concurrency=20,
    rich_sections=True,
)
```

## Choosing a concurrency value

- Start with 10–20 workers for ordinary text hydration.
- Benchmark a fixed item selection at 5, 10, 20 and 40 workers before a large
  acquisition. Record the selection, formats, elapsed time, failures and retry
  counts.
- Reduce concurrency when retries, timeouts or HTTP errors increase. Fast
  completion is not useful if it creates holes in the corpus.
- Keep bounded retries and typed acquisition failures. Never silently omit a
  selected document.
- GPU workers do not accelerate HUDOC HTTP acquisition. They are useful later
  for independent embedding or model stages, which can be sharded separately.
